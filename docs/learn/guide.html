1. The job

Isolation is a security property (tenant A cannot read, write, or starve tenant B). Separate environments are an operational topology (N stacks). The silo design bought isolation by paying O(N) operations. This platform keeps per-tenant databases and makes fleet work scale as waves.

Must be trueHow this repo proves it
No cross-tenant data pathGET /v1/isolation/run plus Django connection manager
Fleet ops are O(waves)One signed release, canary → wave → fleet
Onboarding is a registry writePOST /v1/tenants walks requested → active
Tenants can moveValidated dump/restore, then registry commit
Faults stay containedChaos: one DB down, others healthy

2. How the live website is hosted

Three systems, one GitHub repo. Push to main updates the sources of truth. Render rebuilds the API. Vercel rebuilds the console. Neither stores tenant data on an ephemeral disk as the product of record — the demo registry is in-memory on the control plane (resets on sleep/restart on the free plan).

Important Render constraint: the filesystem is ephemeral. Local SQLite files vanish on restart. The showcase control plane keeps the registry in memory so a free web service can still demonstrate placement, moves, and waves. Production would persist the registry in Postgres and tenant DBs on dedicated storage.

3. What happens when you click in the console

The Next.js app never talks to a database. Every screen is a thin client over frontend/lib/api.js. On localhost it uses http://localhost:8000. On Vercel (hostname not localhost) it uses https://cell-control-plane.onrender.com unless NEXT_PUBLIC_API_URL is set.

5. Placement policy

The policy emits a tier (pooled / dedicated / sovereign). It does not “select CELL-01” as a slogan. Pooled capacity is 8. Overflow creates the next pooled cell (CELL-03 in the demo after CELL-01 and CELL-02 fill).

6. Tenant lifecycle

The controller is idempotent. If it crashes after database_ready, a retry continues from recorded completed_steps. Suspend and resume are registry transitions. Delete is a tombstone, not a silent drop.

7. Data-plane isolation

Django cellapp resolves the tenant from the request, then opens that tenant’s database only. Celery tasks carry an HMAC envelope so a worker cannot run as the wrong tenant. This is L1 isolation: own database, not own Kubernetes cluster.

8. Tenant move

Managed Render Postgres does not give you logical replication between arbitrary tenant databases in this showcase. The move path is validated dump/restore, then a registry commit (epoch++, routing switch). Abort leaves the source authoritative.

9. Wave releases

There is one signed image (digest in the UI). Never N per-tenant deploys. Canary a cell, bake, then the next wave. A bad tenant becomes degraded and is isolated from the wave, not used as a reason to roll the whole fleet by hand.

10. Chaos and I1–I10

Operations → Run I1–I10 posts two live tenant ids and prints PASS/FAIL. Break one tenant DB marks one tenant degraded and returns others_healthy: true. That is the blast-radius demo: one partition fails, the cell and the fleet do not.

IdIntent (short)
I1–I2No request or connection uses another tenant’s database
I3–I5Credentials, cache, and queue payloads are tenant-scoped
I6–I8Backups, restores, and deletes cannot leak across tenants
I9–I10Noisy neighbour and fault containment stay inside a cell / tenant
